* ===========================================================================
* TAKE THE DEBUGGER OFF THE NETWORK. THIS MUST COME FIRST.
*
* The 15:15 launch never opened a window - 59 modules loaded against 145 in a
* working run, stopping in the WMI phase. Cause, from the log:
*
*   *** Unable to resolve unqualified symbol in Bp expression
*       'CardsDLLzf+0x6f8c0' from module 'C:\WINDOWS\SysWOW64\wbemcomn.dll'.
*
* A `bu` on an unmapped module makes cdb treat CardsDLLzf as an UNQUALIFIED
* symbol and hunt for it in EVERY loaded module, on EVERY module load - and
* each hunt forces a symbol load. cdb defaults to `srv*`, the Microsoft symbol
* server with NO local cache (_NT_SYMBOL_PATH is unset everywhere and
* C:\symbols does not exist), so every one of those went to the network and
* cached nothing, with the debuggee suspended throughout.
*
*   .symopt+0x100  SYMOPT_NO_UNQUALIFIED_LOADS - the documented fix for exactly
*                  that message: never search all modules for an unqualified
*                  name.
*   .sympath       a LOCAL directory, no srv*, so the network is unreachable.
*                  We need no Microsoft PDBs: cdb resolves
*                  KERNELBASE!CreateProcessW and SHELL32!ShellExecuteExW from
*                  the export tables, and without PDBs kv prints module+offset,
*                  which is the answer the EA App hunt actually needs.
*
*                  It is "." rather than a named folder, and that is the point.
*                  Any local directory satisfies the requirement - what matters
*                  is that it is NOT a symbol server - and "." is the Game
*                  folder, because launch_fifa.ps1 starts cdb with
*                  -WorkingDirectory $GAME. The absolute path that used to be
*                  here named one machine's research archive, which is exactly
*                  the kind of thing that makes a folder unportable while
*                  looking completely fine on the machine that wrote it.
* ===========================================================================
.symopt+0x100
.sympath .
!sym quiet
.printf "--- symbols: local only, no unqualified loads, no symbol server ---\n"

.printf "--- MINIMAL patch set: runtime-only hooks, statics are baked into the files ---\n"

* THE OOM REPORTER. 0x00b5e7ca is an int 3 the game executes when an allocation
* fails. With no handler cdb HALTS there, which is what presented as the game
* freezing at the FUT hub. This does not fix anything - the allocation still
* returns NULL - but it turns a frozen session into a logged line, so whatever
* happens next is visible. The original script carried this; keep it.
* NAME THE ALLOCATION SITE. 0x00b5e7ca is the int 3, i.e. AFTER the fact;
* 0x00b5e770 is the reporter ENTRY, so this catches the caller before anything
* unwinds. The hub crash asks for 0xFEEA0001 bytes of 'EASTL basic_string' - a
* length read out of freed memory (0xFEEEFEEE is the freed-heap fill), which
* matches the unresolved use-after-free in NEXT_SESSION.md. dps gives the

* Fires only on an OOM, so it costs nothing in normal play.
bp 00b5e770 ".echo ===OOM_BEGIN===; r; dps @esp L20; kv 30; .dump /o /mFhut fut12_oom.dmp; .echo ===OOM_END===; g"

* WINDOW CREATION - MEASURE IT. Two wrong guesses is enough.
*
* fifasetup.ini is CONFIRMED intact and honoured: 11 CRs, FULLSCREEN = 3, mtime
* is our write, and the game did NOT rewrite it. Yet the window still behaves
* like borderless fullscreen. So the tri-state model in NEXT_SESSION.md:65-74 is
* incomplete somewhere, and the next move is a measurement, not another theory.
*
* (Earlier the ini really WAS broken - `sed -i` had stripped every CRLF, 0 CRs
* against the original's 10, so the game fell back to fifasetup_default.ini
* whose FULLSCREEN default is 2 = borderless topmost. That is fixed; the file is
* now written in binary mode with explicit CRLF. This probe proves what the game
* does with it.)
*
*   0x00b9e99c  cmp ebx,1     <- ebx IS the FULLSCREEN value. Settles whether 3
*                                was read, before any branch is taken.
*   0x00b9ea37  call [0x1650648] = CreateWindowExA. Args are already pushed:
*        [esp]=dwExStyle  [esp+4]=lpClassName  [esp+8]=lpWindowName
*        [esp+0xc]=dwStyle  [esp+0x10]=X  [esp+0x14]=Y
*        [esp+0x18]=nWidth  [esp+0x1c]=nHeight
*
* EXPECTED if mode 3 is applied: style=0xcf0000 (WS_OVERLAPPEDWINDOW), ex=0.
* If we see style=0x86000000 / ex=8 instead, it took the mode-1/2 arm and the
* whole tri-state understanding is wrong.
* Both fire exactly ONCE per launch, so they cost nothing.
* WHERE DOES THE 1 COME FROM? Run 6 measured [FSMODE] FULLSCREEN=1 while the
* ini said 3 - and the ini is provably being read, because the SAME reader on
* the SAME settings object [0x1a18560] returned our RESOLUTIONWIDTH/HEIGHT
* (w=1904 h=1041) twelve instructions later. Every write to ebx between the
* read and the branch was traced: the only coercion is 0 -> 1 at 0x00b9e8d5
* (non-Transgaming), so a 3 would survive untouched.
*
* So either the ini LOOKUP returned the default, or the command-line override
* path overwrote it. These two have completely different fixes, and these two
* probes separate them:
*   0x00b9e89f  eax = result of GetIniInt("FULLSCREEN", default=1)   <- the ini
*   0x00b9e8b3  eax = result after the 0xb32c30 override lookup       <- final
* If READ=3 and FINAL=1 the override path is the culprit. If READ=1 the key is
* not being found at all, despite the file containing it.
bp 00b9e89f ".printf \"[FSREAD] ini returned %d\\n\", @eax; g"
bp 00b9e8b3 ".printf \"[FSFINAL] after override %d\\n\", @eax; g"

bp 00b9e99c ".printf \"[FSMODE] FULLSCREEN=%d\\n\", @ebx; g"
bp 00b9ea37 ".printf \"[WND] ex=%p style=%p x=%p y=%p w=%d h=%d\\n\", poi(@esp), poi(@esp+0xc), poi(@esp+0x10), poi(@esp+0x14), poi(@esp+0x18), poi(@esp+0x1c); g"

* CATCH THE CORRUPT STRING BEFORE THE ALLOCATOR EVER SEES IT.
*
* 0x010b5c8c is the thousands-separator insert inside the number formatter:
*   cmp ebp,3 / mov ecx,[esi] / push 0x16599bd / push 0x16599bc (a STATIC
*   1-char ',') / push ecx / call 0x00b979e0 = basic_string::replace()
* replace() then computes  required = (end - begin) + 1  and the measured value
* was 0xFE7C0000 - negative, and an exact multiple of 64 KB, i.e. begin and end
* are in DIFFERENT heap blocks. Since the separator length is a hard-coded 1,
* the only bad term is the string's own (end - begin). The object is already
* corrupt when the formatter receives it.
*
* CONDITIONAL, and on the formatter rather than on replace() itself. A bare
* trap on replace() would fire for every string replace in the game - exactly
* the per-trap cost that caused the old stutter. This site only runs while
* grouping digits, and prints ONLY when the size is impossible, so a healthy
* frame costs one comparison.
bp 010b5c8c ".if (poi(@esi+4)-poi(@esi) > 0x10000) { .echo ===BADSTR===; .printf \"[BADSTR] begin=%p end=%p size=%p pos=%p\\n\", poi(@esi), poi(@esi+4), poi(@esi+4)-poi(@esi), @ecx; r; dps @esp L18; kv 30 }; g"

* an access violation should be logged and continued, not halt the game
* /mFhut, NOT /ma. A full-memory dump of this process is ~800 MB and this
* handler fires on the FIRST chance of EVERY access violation, including any
* the game handles itself - writing 800 MB each time would stall the game. This
* form carries module headers, handles, unloaded modules and thread state,
* which is what was missing last time ("Stack unwind information not
* available"), at a fraction of the size.
*
* FORWARD SLASHES IN THE PATH, DELIBERATELY. Inside a quoted cdb command string
* a backslash is an escape character, so the first attempt at this line wrote
*     Creating C:logscrash.dmp        (from C:\logs\crash.dmp)
* - every separator was swallowed. Win32 accepts forward slashes, and cdb never
* touches them, so this form cannot be mangled.
sxe -c ".echo ===AV_BEGIN===; r; u @eip L3; kv 30; .echo ---RAWSTACK---; dps @esp L40; .dump /o /mFhut fut12_crash.dmp; .echo ===AV_END===; gN" av
